# Launcher UI/UE 重新设计与整改计划

> 目标：全面重构 launcher 的 UI/UE——**UI 全部下沉到服务端、客户端只提供「能力」**，方便后续 UI/UE 迭代更新；同时把三版本管理（正式/预览/开发）的语义可视化到 UI 里。
> 关联文档：[launcher现状梳理与序列图.md](launcher现状梳理与序列图.md) · [launcher代码评审报告.md](launcher代码评审报告.md) · [版本管理与发布方案.md](版本管理与发布方案.md)

## 0. 现状与关键结论

### 0.1 UI 现状盘点

| UI 载体 | 位置 | 现状 | 能否服务端下发 |
|---|---|---|---|
| 激活向导 | `embedded-ui/matrix-setup.html`（47KB，6 个 section）| 深色手写 CSS，单文件内联 | ✅ 已支持（ui_bundle 双轨）|
| 首次欢迎 | `embedded-ui/first-run.html`（3.5KB）| 单屏卡片 | ✅ 已支持 |
| 操作进度 | `embedded-ui/console.html`（7.8KB）| 进度条+步骤+日志+历史 | ✅ 已支持 |
| **托盘菜单** | `tray.rs`（100KB Rust）| **Rust 代码写死**，菜单结构/文案/顺序全硬编码 | ❌ **不支持**（核心缺口）|
| 管理页 | `dsh-launcher-center/views/adminPage.js`（32KB）+ `web/*.js` | 7 个 tab，浅色主题 | ✅ 服务端天然托管 |

### 0.2 关键结论（决定计划方向）

1. **「UI 服务端化」的基础设施已建好一半**：`ui_bundle.rs` 双轨加载 + `/api/ui-bundle` 端点已存在，只覆盖 3 个 HTML 窗口。
2. **最大缺口是托盘菜单**：它是 Rust 硬编码的（100KB），这是同事每天最先看到、最常操作的入口，却无法服务端迭代。
3. **三版本（正式/预览/开发）目前 UI 完全不可见**：同事不知道自己跑在哪个通道、哪个版本组合。
4. 评审发现的 **H7（配置写回破坏边界）+ H8（save_config 非原子）** 是 UI 服务端化的前置地基问题，必须先修。

## 1. 设计规范（我来定一套，无现成规范）

### 1.1 设计语言：三个关键词

- **克制**：少色、少装饰，信息层级靠间距和字重，不靠花哨。
- **可信**：每个操作都有「将要做什么 → 正在做什么 → 结果如何」三态反馈（沿用现有 ops 状态机的好底子）。
- **可感知**：版本、通道、状态这些「看不见的运行时真相」要显性化到 UI。

### 1.2 视觉规范（Design Token）

| Token | 值 | 用途 |
|---|---|---|
| 背景 `--bg` | `#0f1420` | 主背景（比现在更深，减少眩光）|
| 卡片 `--card` | `#1a2130` | 卡片/面板 |
| 卡片边框 `--line` | `#2a3446` | 分隔 |
| 主文本 `--text` | `#e8edf5` | 正文 |
| 次要文本 `--muted` | `#8b96ab` | 说明 |
| 主色 `--primary` | `#4c7dff` | 主按钮/强调（品牌蓝，比现有 #60a5fa 更稳重）|
| 成功 `--success` | `#3ecf8e` | 完成/正式版 |
| 警告 `--warning` | `#f0a84b` | 预览版/待确认 |
| 危险 `--danger` | `#ef5b5b` | 失败/开发版 |
| 字体 | `-apple-system, "Segoe UI", "PingFang SC", "Microsoft YaHei"` | 统一 |
| 圆角 | 卡片 12px / 按钮 8px / 标签 4px | 层级 |
| 间距基准 | 4px 网格（4/8/12/16/24）| 一致 |

### 1.3 语义色 = 通道色（三版本可感知的关键）

| 通道 | 颜色 | 图标 | 语义 |
|---|---|---|---|
| 正式版 stable | `--success` 绿 | ✓ | 稳定、测试过 |
| 预览版 preview | `--warning` 橙 | ⚡ | 灰度、尝鲜 |
| 开发版 dev | `--danger` 红 | 🔧 | 开发者自测、不稳定 |

**这条规则贯穿所有 UI**：托盘菜单、进度窗、管理页都用同一套通道色，同事一眼看出自己在哪个版本。

### 1.4 组件库（服务端 UI 包共享）

统一抽成一份 `ui-kit.css` + `ui-kit.js`（随 UI 包下发），三个窗口 + 管理页共用：

- 按钮：`primary` / `ghost` / `danger` / `warning`
- 状态标签：`chip`（通道徽章）/ `badge`（计数）
- 进度：`progress`（条 + 步骤列表 + 日志）
- 卡片：`card` / `card-title` / `card-desc`
- 表单：`field` / `input` / `select` / `toggle`
- 反馈：`toast` / `modal`（非阻塞，替代 alert/confirm，见 opencli 记忆）

## 2. 架构改造：UI 全服务端化

### 2.1 目标架构

```
服务端（dsh-launcher-center）
  ├─ /api/ui-bundle        下发音 UI 包（HTML/CSS/JS，带版本协商 304）
  ├─ /api/menu             下发托盘菜单结构（JSON，替代 tray.rs 硬编码）★新增
  └─ /api/releases         下发三通道版本组合（见版本方案）
        │
客户端（launcher，只提供能力）
  ├─ 拉取 UI 包 → 缓存 → 窗口渲染（现有 ui_bundle 机制，扩展覆盖范围）
  ├─ 拉取菜单 JSON → 动态构建托盘（★替代 tray.rs 硬编码菜单）
  └─ 提供能力端点（安装/启动/同步/镜像/测速…，IPC/协议不变）
```

### 2.2 关键改造点：托盘菜单「配置化」

现在 `tray.rs` 的 `build_menu()` 把菜单项**硬编码在 Rust 里**（启动/停止/打开/安装/切换Profile/同步/dsh版本/加速/管理能力/日志/退出…）。改造后：

```jsonc
// 服务端 /api/menu 下发（示例）
{
  "version": "20260929.1",
  "groups": [
    { "id": "common", "label": "常用操作", "items": [
      { "id": "launch", "label": "启动数字分身", "capability": "launch", "enabled_when": "!running" },
      { "id": "stop",  "label": "停止数字分身", "capability": "stop",  "enabled_when": "running" }
    ]},
    { "id": "version", "label": "版本", "items": [
      { "id": "ver-info", "label": "当前 v1.3.0（正式版）", "capability": null, "chip": "stable" }
    ]}
  ]
}
```

- **能力（capability）** 是客户端注册的枚举（launch/stop/install/sync/switch-version/…），客户端只提供能力，**不关心菜单长什么样**。
- **文案、顺序、分组、显隐条件、通道徽章** 全部由服务端决定，改菜单不再发版 exe。
- 客户端**只保留最小「启动壳」兜底**：托盘菜单的核心 4 项（启动/停止/打开/退出）内置，其余全部服务端下发（见 2.4）。

### 2.4 「无兜底」的正确语义：预置「启动壳」，下发「内容」

> 脑实验结论（见《UI-UE用户场景脑实验.md》）：托盘菜单是唯一控制入口，断网时不能连「退出」都点不到；首装瞬间 UI 包缓存为空会白屏。因此「无兜底」要分类型，最终收敛为「**只预置一个极小的启动壳，业务内容全下发**」。

| 层 | 内容 | 是否随 exe 预置 | 变化频率 |
|---|---|---|---|
| **启动壳（Capability Shell）** | 窗口能打开、显示「正在连接服务端/首次配置中」+ 重试按钮、连本机能力端点、托盘菜单核心 4 项 | ✅ **预置（最小，几 KB）** | 几乎不变 |
| **主题与组件库 ui-kit** | 配色 Token、按钮/标签/进度/通道徽章 | ❌ 服务端下发 | 低频（改规范才变）|
| **内容 UI（页面/文案/流程/菜单项）** | 激活向导步骤、进度文案、版本徽章展示、菜单顺序文案 | ❌ **纯服务端下发** | 高频（快速迭代）|

**首装体验**：壳先显示「正在连接服务端 / 首次配置中…」+ 重试按钮 → 同步拿到 UI 包后无缝切换到完整 UI。断网时壳 + 缓存的旧 UI 包仍可用（缓存即兜底）。

### 2.3 覆盖范围扩展

| UI | 现在 | 改造后 |
|---|---|---|
| 激活向导 / 首屏 / 进度 | 服务端可下发 | 保持，纳入新设计规范 + ui-kit |
| 托盘菜单 | Rust 硬编码 | 服务端菜单 JSON 下发 |
| 管理页 | 服务端托管 | 保持，纳入 ui-kit + 三版本管理 tab |
| **版本/通道信息** | 无 | 新增「版本通道徽章」贯穿所有 UI |

## 3. 三版本管理的 UE 设计（核心新能力）

### 3.1 同事端可感知「自己在哪个版本」

托盘菜单顶部 + 进度窗 + 向导，统一展示：

```
┌─────────────────────────────┐
│  数字分身  v1.3.0  [✓正式]   │  ← 通道徽章：绿=正式/橙=预览/红=开发
│  ───────────────────────    │
│  启动数字分身                │
│  打开页面                    │
│  ...                        │
└─────────────────────────────┘
```

### 3.2 版本切换的 UE

- 托盘「版本」子菜单：列出可切换的通道（正式/预览/开发），当前通道打 ✓，非当前通道显示「切换到预览版」。
- 切换前弹**非阻塞确认**（复用 toast/modal，不用 alert）：明确告知「将切换到预览版 v1.4.0-preview.1，包含以下变更…」。
- 切换后进度窗显示「正在对齐版本 v1.4.0-preview.1（预览通道）」。

### 3.3 管理页新增「版本管理」tab

- 三通道卡片（正式/预览/开发），每张显示当前版本组合（dsh 版本 + 插件清单 + 岗位）。
- 「发布」流程可视化：开发 → 升预览 → 测试 → 升正式，带「测试通过」门禁按钮。
- 灰度名单管理（哪些客户端/账号进预览/开发）。

## 6. 决策记录（已拍板 ✅ / 待确认 ❓）

**已拍板（本轮确定）：**

1. ✅ **托盘菜单配置化**：走服务端 `/api/menu` JSON 下发 + 客户端能力枚举，但保留最小「启动壳」兜底（核心 4 项：启动/停止/打开/退出）。
2. ✅ **客户端不保留完整兜底 UI**：展示型窗口（激活向导/首屏/进度）彻底服务端化，只预置极小的「启动壳」。
3. ✅ **设计规范**：我定的这套（深色 #0f1420 + 主色 #4c7dff + 通道色语义 + ui-kit）。
4. ✅ **UI 包预置分发**：只预置「最小、最不会变的启动壳」，业务内容（文案/步骤/菜单项）全部服务端下发。
5. ✅ **首装体验**：壳先显示「连接中/首次配置中」+ 重试，拿到 UI 包后无缝切换完整 UI。

**待确认：**

1. ❓ **阶段顺序**：同意「先修地基（阶段0）→ UI 服务端化（阶段1）→ 同事端重设计（阶段2）」吗？还是想先看视觉重设计效果再动架构？
2. ❓ **并行度**：阶段 2/3/4 是否拆多子任务并行推进（用工作流），还是按顺序逐个来？
3. ❓ **版本方案决策点**（影响阶段 3）：岗位是否进版本 / 灰度按机器还是按人 / 「测试通过」由谁判定 / 是否要一键回滚（见《版本管理与发布方案.md》第 6 节）。
