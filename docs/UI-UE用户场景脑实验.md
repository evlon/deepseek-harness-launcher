# 用户场景脑实验：验证「UI 全服务端化 + 无兜底 + 托盘菜单配置化」

> 目的：在动手改造前，用真实用户场景走查一遍，验证三个决定（托盘菜单配置化 / 客户端无兜底 UI / 设计规范自定）会不会在某些场景翻车，找出必须提前处理的坑。

---

## 关键事实（脑实验的前提，已核对源码）

1. **UI 加载时序**：客户端启动 → `setup` 里 `load_config` → 异步 `sync::spawn_sync_loop`（配了 serverUrl 才启，默认 5 分钟一轮）→ 同步成功后才拉 UI 包缓存。**首次启动的瞬间，UI 包缓存是空的**。
2. **三个窗口**（first-run / matrix-setup / op-console）都是「打开时才读 HTML」：`ui_bundle::load_html(缓存版) ?? 内置兜底`。
3. **托盘菜单**现在由 `tray.rs::build_menu()` 在**启动瞬间同步构建**，硬编码，**不依赖网络**。
4. **首装场景**：同事第一次双击，`needs_onboarding` 判定 true → 弹 first-run 首屏 → 引导装依赖 + 激活。此时可能**还没配 serverUrl、或服务端连不上**。

---

## 场景走查

### 场景 1：同事第一次双击（首装，服务端可达）⭐ 最容易翻车

- 双击 → `setup` 里 `load_config`（此时 serverUrl 可能还没配置，或配置了但同步循环还没跑完第一轮）。
- `needs_onboarding` → 弹 first-run 首屏 → 需要读 first-run 的 HTML。
- **如果「无兜底」**：此时 UI 包缓存为空（同步还没跑完/还没配 serverUrl）→ `load_html` 无缓存 → **白屏**。

**结论：🔴 高风险**。「无兜底」在首装瞬间会白屏，除非满足下面任一前置条件：
- (a) first-run 首屏 HTML 仍编译期内嵌（不参与「无兜底」）；或
- (b) 首装流程先强制同步拉 UI 包（阻塞等待），拉不到才给一个极简「纯文本/系统对话框」提示。

**建议**：**「无兜底」要分窗口对待**——首装入口（first-run）必须有最小可用的降级（哪怕只是「正在连接服务器…」占位 + 重试按钮），否则小白首装直接白屏是灾难。

### 场景 2：同事断网 / 服务端宕机时打开窗口

- 已配 serverUrl，但某天服务端宕机或本机断网。
- 用户点托盘「打开页面」「查看进度」→ 窗口需要读 HTML。
- **如果「无兜底」且缓存已有**：读本地缓存的旧 UI 包（`load_html_from_dir` 会读缓存文件，不联网）→ **能显示**（旧版本 UI）。
- **如果「无兜底」且缓存为空**（从未成功同步过）→ 白屏。

**结论：🟡 中风险**。「无兜底」意味着「**缓存即兜底**」——只要同步成功过一次、UI 包落盘了，断网仍能用（这是现有 ui_bundle 机制就支持的）。真正的问题只剩「从未同步成功过」的机器。**建议：UI 包缓存视为必须持久化、且安装包可预置一份随 exe 分发**（见场景 5 的解法）。

### 场景 3：托盘菜单配置化后，服务端连不上

- 托盘菜单改成「服务端 JSON 下发」。
- 断网/服务端宕机 → 拉不到菜单 JSON。
- **「客户端不要兜底 UI」若也适用于菜单**：托盘菜单为空 → 用户**连「退出」「启动」都点不到**，程序只能从任务管理器强杀。🔴 灾难。

**结论：🔴 高风险**。托盘菜单是**程序唯一的控制入口**，不能没有兜底。菜单「配置化」不等于「无兜底」——**菜单必须保留一个最小的内置默认结构**（启动/停止/打开/退出 这几项核心项），服务端 JSON 只是「覆盖/增强」它。这与「无兜底 UI」是两个概念，要分开决策。

> ⚠️ 这是脑实验最重要的发现：**「无兜底」能用于「展示型窗口 UI」，绝不能用于「控制型托盘菜单」**。否则断网时用户连退出都做不到。

### 场景 4：服务端下发了一个有 bug 的 UI 包

- 管理员改 UI 发版，结果 HTML 里 JS 报错 / 样式崩了。
- 所有同事同步后拉到坏 UI → 激活向导/进度窗全崩。

**结论：🟡 中风险**。现有机制有保护：`load_html_from_dir` 逐文件校验（含 `<html`、≤512KB、*.html 白名单），但**不校验 JS 语法/渲染正确性**。坏 UI 会「校验通过但渲染崩」。
**建议**：管理页「UI 包」加一个「预览 + 灰度发布」能力（先发到 preview 通道的客户端，验证 OK 再全量），或至少加「一键回滚到上一个版本」（服务端保留历史版本号，客户端 `load_html_from_dir` 已按版本号从大到小尝试，天然支持回滚到旧缓存）。

### 场景 5：UI 包体积 / 拉取时机

- 现在单文件 ≤512KB、三窗口合计可能 1MB+。若未来 UI 更复杂（多文件、图片、字体），`/api/ui-bundle` 一次拉全量，同步时下载慢。
- 首装时「强制拉 UI 包」会拖慢首次激活。

**结论：🟢 低风险（当前）但需预留**。当前三窗口是单文件 HTML + 内联 CSS/JS，体积可控。**建议**：UI 包设计为「版本号 + 文件清单 + 增量」，且**首装包可随 launcher exe 一起分发预置**（把 UI 包打进安装 zip，落到缓存目录），这样「首装白屏」和「从未同步过」两个风险一并消除。

### 场景 6：三版本 UE 在「无兜底」下的表现

- 版本通道徽章、切换入口，依赖服务端下发的菜单 JSON + releases 数据。
- 断网时：通道信息拉不到 → 徽章显示「未知」，切换入口不可用。

**结论：🟢 可接受**。版本信息本就来自服务端，断网时显示「未知/离线」是合理的。**但**要保证：断网时**核心操作（启动/停止/打开）仍可用**（回到场景 3 的最小兜底菜单），版本徽章只是「附加信息」降级，不能拖累核心功能。

---

## 脑实验总结：必须守住的三条底线

| # | 底线 | 为什么 | 落地方式 |
|---|---|---|---|
| 1 | **托盘菜单必须有最小内置兜底**（启动/停止/打开/退出）| 菜单是唯一控制入口，无兜底则断网无法退出 | 服务端 JSON 只「覆盖/增强」，客户端保留核心项内置 |
| 2 | **首装/未同步过的机器不能白屏** | 首装是小白第一印象，白屏=灾难 | UI 包随 exe 预置分发，或首装强制拉取+降级提示 |
| 3 | **UI 包要有「回滚 + 灰度」能力** | 坏 UI 全量下发会团灭 | 服务端保留版本历史 + 管理页回滚；preview 通道先灰度 |

---

## 对原计划的修正（基于脑实验）

原计划「客户端不要兜底 UI」需要**细化**，改成：

1. **展示型窗口（激活向导/首屏/进度）**：可「无编译期内置兜底」，但**必须有「缓存兜底 + 安装包预置」**（UI 包随 exe 分发，落缓存目录），保证首装/断网可用。
2. **控制型托盘菜单**：**保留最小内置兜底结构**（核心 4 项），服务端 JSON 只做覆盖/增强——「配置化」≠「无兜底」。
3. **新增能力**：管理页 UI 包「灰度发布 + 一键回滚」，作为「无兜底」的安全网。

这三条修正不改变你「UI 全服务端、客户端只提供能力」的大方向，只是把「无兜底」从「一刀切」收敛为「分类型」——展示型可彻底服务端化，控制型必须留最小内核。
