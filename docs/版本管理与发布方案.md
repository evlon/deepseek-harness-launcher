# 数字人版本管理与发布方案（三版本 + 三通道）

> 目标：解决「launcher 每次安装版本、每次更新都有风险，同事更新不顺利」的问题，
> 把现在割裂的「DSH 版本 / 插件清单 / 岗位清单」收口成一套**可配置、可测试、可分级的版本组合 + 发布通道**体系。
> 本文是**方案设计**（现状见《launcher现状梳理与序列图.md》，代码评审见评审报告）。

---

## 1. 核心概念：一个「版本」= 一份「版本组合」

你定义的数字人版本，是**一组组件的版本快照**，而不是单个数字：

```yaml
# 一个「数字人版本」（版本组合 Manifest）长这样：
releaseId: "v1.3.0"              # 版本号（人类可读，服务端唯一）
dsh: "0.1.7-rc.2"                # DSH 核心版本（精确锁定）
plugins:                          # 定制插件版本清单（精确锁定，不再是裸名）
  dsh-matrix-agent: "0.3.10"
  dsh-codebuddy-models: "1.2.0"
  dsh-nested-followups: "0.2.2"
  "@noob-stupid/dsh-plugin-console": "0.1.4"
  launcher-brand: "1.0.0"
jobs:                             # 岗位（技能）清单
  - "reception"                   # 接待
  - "secretary"                   # 秘书
```

**关键变化**：现在的 `plugins` 是「裸名字、装 latest」，改成「名字:版本，精确锁定」——
这是「每次更新都有风险」的根因之一：**同事每次装 latest，插件组合不可复现**，今天和明天装的不是同一套。

---

## 2. 三通道：正式 / 预览 / 开发

通道解决「**同一个版本号，对不同受众有不同的可见性**」。

| 通道 | 英文 | 受众 | 语义 | 测试门禁 |
|---|---|---|---|---|
| **正式版** | `stable` | 全体同事 | 服务端配置的、**测试过**的版本组合 | ✅ 必须过测试（冒烟/回归）才能发布 |
| **预览版** | `preview` | 灰度用户（部分同事）| 灰度发布的版本组合，先小范围验证 | 🟡 建议过基础冒烟，不强制全量回归 |
| **开发版** | `dev` | 开发者 | 开发者启动配置后看到的版本，方便自测 | ❌ 无门禁，随意 |

### 2.1 服务端数据结构（新增，兼容现有 config.json）

```jsonc
// data/config.json 新增 releases 段（与现有 plugins/profilePlugins 并存，逐步迁移）
{
  "releases": {
    "stable": {
      "releaseId": "v1.3.0",
      "dsh": "0.1.7-rc.2",
      "plugins": { "dsh-matrix-agent": "0.3.10", "..." : "..." },
      "jobs": ["reception", "secretary"],
      "tested": true,              // 是否已通过测试门禁
      "publishedAt": "2026-09-29T10:00:00Z"
    },
    "preview": {
      "releaseId": "v1.4.0-preview.1",
      "dsh": "0.1.8-rc.1",
      "plugins": { "...": "..." },
      "jobs": ["..."],
      "tested": false,
      "publishedAt": "..."
    },
    "dev": {
      "releaseId": "dev-latest",
      "dsh": "latest",              // dev 通道允许不锁定，跟最新
      "plugins": { "dsh-matrix-agent": "latest" },
      "jobs": []
    }
  },
  // 灰度名单：哪些 clientId / 账号进 preview 通道
  "previewClients": ["client-uuid-1", "client-uuid-2"],
  "devClients": ["client-uuid-3"]
}
```

### 2.2 客户端通道选择逻辑

```
客户端启动/同步时，按优先级决定自己属于哪个通道：
1. devClients 名单命中（或本地配置 dshChannel=dev）→ dev 通道
2. previewClients 名单命中（或本地配置 dshChannel=preview）→ preview 通道
3. 其余 → stable 通道（默认，最安全）
```

- 通道由**服务端灰度名单**控制，也可**本地配置**覆盖（开发者自测用）。
- 客户端拿到自己通道对应的 `releases[channel]`，按 manifest 精确安装/校验。

## 3. 客户端配合改造点（launcher 需要开发的功能）

### 3.1 版本组合的「安装/校验」

- 现在的 `install_server_recommended` 用「裸名装 latest」，改为**按 manifest 的 `plugins` 精确 `name@version` 安装**（`pnpm add name@version`）。
- 新增「**版本一致性校验**」：启动/同步时对比「本机已装版本组合」 vs 「服务端 manifest」，不一致则提示/自动对齐。

### 3.2 dsh 版本接入组合

- 现有 `dshVersion` 固定版本机制**升级为** manifest 里的 `dsh` 字段（同一来源，不再单列）。
- `dshChannel`（rc/alpha）**并入**三通道语义：stable 通道 = 只出测试过的固定 dsh 版本；dev 通道 = 允许跟 latest/alpha。

### 3.3 岗位接入组合

- `jobPresets` 并入 manifest 的 `jobs` 字段，与插件版本一起锁定，保证「某版本的岗位技能」可复现。

### 3.4 托盘/进度 UI

- 托盘「dsh 版本」子菜单 → 升级为「**数字人版本**」子菜单，显示：当前版本号 + 当前通道（正式/预览/开发）+ 可切换的通道。
- 进度窗口显示「正在对齐版本 v1.3.0（正式通道）」而非笼统的「安装服务器推荐插件」。

## 4. 测试门禁（「测试过才能定义为发布版本」的落地）

### 4.1 发布流程（正式版）

```
开发 → 打 manifest（dev 通道自测）→ 升 preview（灰度）→ 测试通过 → 升 stable（全量）
        ↑ 开发者自测              ↑ 灰度用户验证        ↑ 门禁：tested=true 才可见
```

### 4.2 测试门禁的具体做法（建议最小可行）

| 层级 | 做法 | 工具/载体 |
|---|---|---|
| **冒烟测试** | 新 manifest 在 CI 里装一遍（Node+pnpm+dsh+插件），启动 dsh 验证 bin 可达、端口就绪 | 复用 launcher `--cmd test` 全流程自测 |
| **回归测试** | 关键插件（matrix-agent 等）做最小功能断言 | 现有 tests/ + 新增 manifest 级测试 |
| **灰度验证** | preview 通道先放给灰度用户 N 天，观察上报的「启动失败/插件崩溃」指标 | 服务端已有 clients 状态收集，加健康指标 |

- 服务端 `releases.stable` 的 `tested` 字段**由测试流程置 true**，管理页 UI 提供「标记为已测试」按钮（配合人工确认），**未测试过的 stable 不生效**。
- 这是把「测试过才算发布」从口头约定变成**代码强制**。

## 5. 迁移路径（不破坏现有同事）

1. **第一步（最小改动）**：服务端 `plugins` 清单升级为支持 `name@version` 格式（客户端 `install_plugin` 已支持 spec 格式），先实现「插件版本锁定」，不动整体架构。
2. **第二步**：新增 `releases` 三通道结构 + 客户端通道选择 + manifest 精确安装，与旧的 `plugins/profilePlugins/dshVersion/jobPresets` **并行**（新字段优先，旧字段兜底）。
3. **第三步**：灰度切换——把灰度用户切到 preview 通道验证，稳定后全量切 stable。
4. **第四步**：测试门禁自动化 + 旧字段下线。

## 6. 需要与你确认的关键决策点

1. **版本组合的粒度**：是否要把「岗位(jobs)」也锁进版本？还是岗位独立于版本（岗位是技能，版本是运行时）？
2. **灰度粒度**：按 clientId（机器）还是按账号（人）灰度？
3. **dev 通道的可见性**：dev 通道要不要对普通同事**完全隐藏**（只在开发者本地配置才出现），还是托盘可见但标红「开发版」？
4. **「测试过」的判定**：由 CI 自动测试判定，还是人工在管理页点「确认已测试」？还是两者都要？
5. **回滚能力**：正式版发布后发现问题，要不要支持「一键回滚到上一个 stable 版本」（服务端保留历史 manifest）？

---

## 7. 与现有机制的关系映射（收口对照表）

| 现有机制 | 升级后归属 |
|---|---|
| `plugins`（裸名清单）| → manifest.plugins（名字:版本）|
| `profilePlugins`（按 profile）| → manifest.plugins（必要时按 profile 拆分，或保留 profile 维度）|
| `dshVersion`（固定 dsh）| → manifest.dsh |
| `dshChannel`（rc/alpha）| → 三通道（stable/preview/dev）|
| `jobPresets`（岗位清单）| → manifest.jobs |
| launcher 自身版本（三处）| 保持独立（launcher 是「载体」，不是「数字人版本」的一部分，与你的「不应包含 launcher 自身」一致）|
